# Contributing to Cubiq

Cubiq is a Minecraft Java Edition server built as a set of patches on top of
[Purpur](https://github.com/PurpurMC/Purpur), which itself patches
[Paper](https://github.com/PaperMC/Paper). This guide explains how the source tree is
generated, where changes belong, and how to validate them before opening a pull request.

## Requirements

- **JDK 25.** Minecraft 26.3 and Paper 26.3 require Java 25. Any vendor works
  (Temurin, Corretto, ...). Gradle toolchains detect installed JDKs; point Gradle at a JDK
  with `org.gradle.java.installations.paths` in `~/.gradle/gradle.properties` if needed.
- **Git** with `user.name` and `user.email` configured. paperweight creates local commits
  while applying patches.
- **Network access** to GitHub (the Purpur and Paper repositories are cloned), Mojang
  (`piston-meta.mojang.com`, `piston-data.mojang.com`), `repo.papermc.io`, Maven Central and
  the Gradle Plugin Portal.
- Several GB of free disk space and memory: the Minecraft server is downloaded, decompiled
  and patched locally.

Clone the repository with Git. Downloading a zip archive does not work because the build
applies patches with Git.

## Getting started

```bash
git clone https://github.com/PwiePixel/Cubiq.git
cd Cubiq
./gradlew applyAllPatches      # sets up all generated source trees
./gradlew createPaperclipJar   # builds cubiq-server/build/libs/cubiq-paperclip-<version>.jar
```

`applyAllPatches` clones Purpur at the commit pinned by `purpurCommit` in
`gradle.properties`, lets Purpur apply its own patches to Paper, downloads and decompiles
the Minecraft server, and finally applies Paper's, Purpur's and Cubiq's patches in that order.

## Repository layout

Tracked in Git:

| Path | Contents |
| --- | --- |
| `build.gradle.kts`, `settings.gradle.kts`, `gradle.properties` | Patcher configuration and the upstream pin (`purpurCommit`) |
| `cubiq-api/` | `build.gradle.kts.patch`, `paper-patches/` (changes to Paper's API), `purpur-patches/` (changes to Purpur's API), `src/` (Cubiq API classes) |
| `cubiq-server/` | `build.gradle.kts.patch`, `minecraft-patches/` (changes to Minecraft), `paper-patches/` (changes to Paper/CraftBukkit server code), `purpur-patches/` (changes to Purpur server code), `src/main/java` (Cubiq server classes), `src/test/java` (Cubiq tests) |
| `cubiq-checkstyle/` | `build.gradle.kts.patch` for the checkstyle rules applied to the API |
| `build-data/` | `cubiq.at` (access transformers) and `dev-imports.txt` |
| `licenses/`, `LICENSE`, `NOTICE` | License texts and notices, see [LICENSING.md](LICENSING.md) |

Generated by `applyAllPatches` and ignored by Git:

| Path | Contents |
| --- | --- |
| `paper-api/`, `purpur-api/` | Upstream API sources with Cubiq's API patches applied |
| `paper-server/`, `purpur-server/` | Upstream server sources (CraftBukkit, Paper, Purpur) with Cubiq's patches applied |
| `cubiq-server/src/minecraft/` | Patched Minecraft sources and resources |
| `paper-checkstyle/`, `.checkstyle/` | Upstream checkstyle rules |
| `cubiq-*/build.gradle.kts` | Build scripts generated from Purpur's scripts plus Cubiq's `build.gradle.kts.patch` |

Every generated directory is its own Git repository. Upstream changes appear as commits,
and Cubiq's per-file changes live in a commit named `cubiq <name> File Patches`. Never commit
edits to generated directories to the Cubiq repository directly: turn them into patches with
the tasks below, otherwise they are lost on the next `applyAllPatches`.

## Where a change belongs

Prefer adding new classes under `studio.cubiq` and calling them from small hooks in upstream
code. New files need no patches and are much easier to keep working across upstream updates.

| You want to change | Edit files in | Then run |
| --- | --- | --- |
| Cubiq server code | `cubiq-server/src/main/java/studio/cubiq/` | nothing, the files are tracked directly |
| Cubiq tests | `cubiq-server/src/test/java/studio/cubiq/` | nothing |
| Minecraft code (`net.minecraft.*`) | `cubiq-server/src/minecraft/java/` | `./gradlew :cubiq-server:fixupMinecraftSourcePatches`, then `./gradlew :cubiq-server:rebuildMinecraftSourcePatches` |
| Minecraft resources | `cubiq-server/src/minecraft/resources/` | `fixupMinecraftResourcePatches`, then `rebuildMinecraftResourcePatches` (in `:cubiq-server`) |
| Paper / CraftBukkit / Spigot server code | `paper-server/` | `./gradlew :cubiq-server:fixupPaperServerFilePatches`, then `./gradlew :cubiq-server:rebuildPaperServerFilePatches` |
| Purpur server code | `purpur-server/` | `fixupPurpurServerFilePatches`, then `rebuildPurpurServerFilePatches` (in `:cubiq-server`) |
| Paper API | `paper-api/` | `./gradlew fixupPaperApiFilePatches`, then `./gradlew rebuildPaperApiFilePatches` |
| Purpur API | `purpur-api/` | `./gradlew fixupPurpurApiFilePatches`, then `./gradlew rebuildPurpurApiFilePatches` |
| A build script | `cubiq-api/`, `cubiq-server/` or `cubiq-checkstyle/build.gradle.kts` | `./gradlew rebuildPurpurSingleFilePatches` |

`fixup*FilePatches` stages every change in that generated repository and squashes it into the
file patches commit. `rebuild*FilePatches` then writes the per-file `.patch` files. Review the
resulting diff in the Cubiq repository before committing.

### File patches and feature patches

File patches (the default above) are small per-file diffs and are the right choice for most
changes. Large features that touch many upstream files and should stay one reviewable unit can
instead be committed as their own commit inside the generated repository, on top of the file
patches commit, and exported with the matching `rebuild*FeaturePatches` task (for example
`./gradlew :cubiq-server:rebuildMinecraftFeaturePatches`). Purpur's
[contributing guide](https://github.com/PurpurMC/Purpur/blob/HEAD/CONTRIBUTING.md) describes the
same workflow in more detail.

### Access transformers and library imports

To widen the visibility of a Minecraft member, add an access transformer to `build-data/cubiq.at`
and run `applyAllPatches` again. To patch a source file from a Minecraft library (for example
authlib or DataFixerUpper), list it in `build-data/dev-imports.txt`.

## Conventions for patched upstream code

- Mark every change so that it can be found when updating upstream:
  - `// Cubiq - <reason>` at the end of a single changed line,
  - `// Cubiq start - <reason>` and `// Cubiq end - <reason>` around blocks.
- When changing a line that already carries upstream markers, keep them and append yours,
  for example `// Paper // Purpur - Rebrand // Cubiq - Rebrand`.
- In Minecraft sources, use fully qualified class names instead of adding imports. This keeps
  patches small and avoids conflicts.
- Never reformat upstream code and keep each patch as small as possible.
- User-facing text must not tell people to report Cubiq problems to Paper or Purpur. Use
  `studio.cubiq.Cubiq.ISSUES_URL`.

## Building and testing

```bash
./gradlew build                 # compile everything, run tests and checks
./gradlew createPaperclipJar    # cubiq-server/build/libs/cubiq-paperclip-<version>.jar
./gradlew :cubiq-server:test --tests 'studio.cubiq.testing.*'   # only Cubiq's tests
```

- The server test task only runs classes named `*TestSuite`. Cubiq's plain unit tests live under
  `studio.cubiq` and are collected by `studio.cubiq.testing.CubiqUnitTestSuite`.
- Tests that need Minecraft's registries or a dummy server are annotated with `@Normal` (from
  `org.bukkit.support.environment`) and run by `studio.cubiq.testing.CubiqNormalTestSuite`. Tests for the other
  upstream environments (`@VanillaFeature`, `@AllFeatures`) need a matching suite that sets the `TestSuite`
  configuration parameter; see `paper-server/src/test/java/org/bukkit/support/suite/`.
- Every behavior change needs a test, and every fixed bug needs a regression test. Make sure a new
  test fails without the change it covers.
- Checkstyle is enforced for the API modules, following Paper's rules.

### Smoke tests

The scripts in `scripts/` start a real server from the Paperclip jar. They pass `-Dcom.mojang.eula.agree=true`, so
only run them if you accept the [Minecraft EULA](https://aka.ms/MinecraftEULA).

```bash
# First start in a new directory, then a start with the existing files
SMOKE_EXPECT_CLEAN_CONFIG=true scripts/smoke-test.sh cubiq-server/build/libs/cubiq-paperclip-*.jar run/smoke
SMOKE_EXPECT_CLEAN_CONFIG=true scripts/smoke-test.sh cubiq-server/build/libs/cubiq-paperclip-*.jar run/smoke
# Two starts with a mistake in each kind of checked file, on a copy of the directory (run/smoke-config-check);
# the second one simulates an update of paper-global.yml from an older version
scripts/config-smoke-test.sh cubiq-server/build/libs/cubiq-paperclip-*.jar run/smoke
# A start with a test plugin whose lifecycle steps are slow; needs a server that was started before
scripts/lifecycle-smoke-test.sh cubiq-server/build/libs/cubiq-paperclip-*.jar run/smoke
# A start with a test plugin that blocks the server thread on a lock for 15 seconds
scripts/watchdog-smoke-test.sh cubiq-server/build/libs/cubiq-paperclip-*.jar run/smoke
```

`smoke-test.sh`, which the other scripts use to start the server, uses `java` from the `PATH` unless `JAVA` points to
a Java 25 executable; the lifecycle and watchdog scripts compile their test plugins with `javac` from `JAVA_HOME`.
The scripts fail with an excerpt of the server log when the server does not start or stop cleanly or an expected
message is missing.

`scripts/check-distribution.sh <paperclip-jar> [<server-directory>]` checks the jar server owners download: license
texts and notices included and unchanged, no Minecraft or Mojang classes outside the server patch, fixed entry times.

`scripts/library-licenses.py <paperclip-jar> > docs/LIBRARIES.md` regenerates the list of bundled libraries and their
licenses from the jar and the Maven POMs in the Gradle cache. Run it after changing dependencies or updating
upstream and commit the result. When it reports a license name or a license that `scripts/library-licenses.json` does
not cover, check that the license is compatible with the GPLv3 before adding it there.

The script also fails when a bundled library whose jar contains no license or notice file has no entry in
`scripts/library-notices.json` for its bundled version, or when a library with an entry changes its version. A
library whose jar contains license files needs an entry as well when they lack notices that apply to its code, for
example the notices of code of other projects or of startup code in its native libraries, or when its license
requires recipients to be told where its source code is and its jar does not say it; the script cannot detect this,
so check every new library and version yourself. Code of other projects that Paper, Purpur or Cubiq compile into the
server jar, or that the Paperclip jar contains, needs an entry under `embedded`. For each of them:

1. Find the commit of the library's source that matches the bundled version, for example its release tag, and check
   that it matches the jar (for example by comparing the sources jar or the classes).
2. Collect the license and notice files of the project at that commit, and those of code of other projects that the
   jar contains (relocated libraries, statically linked code in native libraries). Never write a license text by hand.
3. Put them into `licenses/third-party/<project>/` unchanged, and record each file under `files` in
   `scripts/library-notices.json` with its repository, commit, path and SHA-256, or, only for a project that has no
   license file of its own, with the URL of the license text it refers to and its SHA-256. Fetch each file once more
   from that source and compare it byte for byte.
4. Update the library's entry under `libraries`: version, license expression (SPDX), source, files, copyright notices
   (a list, possibly empty) and a note (possibly empty) on the code of other projects it contains. Set `noticesInJar`
   to `true` when the jar contains license or notice files of its own; the entry then lists only the files that the
   jar lacks, possibly none if the entry only records where the source code is. Entries under `embedded` also say
   where the code is (`in`).
5. Regenerate `licenses/THIRD-PARTY-NOTICES.md` with `scripts/library-licenses.py --notices` and
   [LIBRARIES.md](LIBRARIES.md), and remove files that no entry uses any more; the script fails on those as well.

The server jar and the Paperclip jar are reproducible: building the same commit twice in the same environment produces
identical files, which CI checks on every push. Two things break this:

- javac names the temporary variables of increments, decrements and compound assignments such as `+=` of boxed values
  through another object, for example `pair.left++` with an `Integer` field, after hash codes, which differ between
  builds. Write `pair.left = pair.left + 1` instead; CI's check fails otherwise.
- An incremental build can compile a class differently from a complete build, for example when javac takes the
  parameter names of a superclass constructor from source code in one build and from a class file in another. CI
  only makes complete builds. Compare local jars only from complete builds, for example with
  `./gradlew createPaperclipJar --rerun-tasks --no-build-cache`.

The manifest of the server jar records the build time, the branch, the build number and, for a
[release](#releases), its version. Local builds use the epoch as build time, CI uses the commit time
(`BUILD_STARTED_AT`, see `.github/workflows/build.yml`). To build a commit the way CI does, check it out on a branch
with the same name as in CI, leave `BUILD_NUMBER` and `CUBIQ_VERSION` unset, or for a release set them to the values
that its manifest shows as `Build-Number` and `Cubiq-Version`, and build it in a fresh clone:

```
export BUILD_STARTED_AT=$(TZ=UTC git log -1 --format=%cd --date=format-local:%Y-%m-%dT%H:%M:%SZ)
./gradlew applyAllPatches
./gradlew createPaperclipJar --no-build-cache
sha256sum cubiq-server/build/libs/cubiq-paperclip-*.jar
```

The SHA-256 must be the one that the summary of the CI run of that commit shows, for a release also the one in the
`.sha256` file of the release. This was checked for two commits,
45f6cb6 and 05279aa: builds in a fresh clone on another machine, with Amazon Corretto 25.0.5 on Ubuntu 24.04, produced
Paperclip jars identical to those of CI, which used Eclipse Temurin 25.0.4 and 25.0.5 on Ubuntu 26.04. The directory of
the clone and the Maven repository the dependencies came from (Maven Central or a mirror of it) differed as well. What
has to match is the commit, the branch name, `BUILD_STARTED_AT`, `BUILD_NUMBER` and `CUBIQ_VERSION`. A JDK other than
version 25 could compile classes differently, which has not been tried.

Running a server locally (for example with `./gradlew :cubiq-server:runDevServer` or by starting the
Paperclip jar) requires accepting the [Minecraft EULA](https://aka.ms/MinecraftEULA). Upstream's run
tasks request a JetBrains Runtime 25 toolchain; starting the Paperclip jar with any JDK 25 works too.

## Updating upstream

1. Update `purpurCommit` in `gradle.properties`. Purpur pins its own Paper commit, so this also
   moves Paper. If the Minecraft version changes, update `mcVersion` and `apiVersion` too.
2. Run `./gradlew applyAllPatches`. If one of Cubiq's patches no longer applies, paperweight reports it
   and writes the failing hunks to the `rejected/` directory of that patch set (for example
   `cubiq-server/minecraft-patches/rejected/`). Resolve them in the generated sources, rebuild the
   affected patches as described above and delete the rejects.
3. Run `./gradlew build createPaperclipJar` and the [smoke tests](#smoke-tests).
4. Check whether the upstream license files changed and refresh the copies in `licenses/`.
5. Regenerate [LIBRARIES.md](LIBRARIES.md) with `scripts/library-licenses.py` and review new libraries and licenses;
   collect the license notices of libraries that are new or changed their version as described in
   [Smoke tests](#smoke-tests).

## Releases

CI publishes every build of `main` that passes all checks as a pre-release on GitHub. The build job of
`.github/workflows/build.yml` determines the version of the release, builds the jars with it and runs all checks; then
the `release` job tags the commit and creates the release with the Paperclip jar of that build. Nothing is tagged or
uploaded by hand.

- **Versions** have the form `MAJOR.MINOR.PATCH` and are tagged `vMAJOR.MINOR.PATCH`. `cubiqVersion` in
  `gradle.properties` sets `MAJOR.MINOR`, and `scripts/release-version.py` numbers its releases by the patch number,
  after the existing release tags: 0.0.1, 0.0.2 and so on, and after raising `cubiqVersion` to 0.1, the next release
  is 0.1.0. Raise it in the commit that starts the new version; a `cubiqVersion` below the latest release fails the
  build. A release also gets a build number, the number of releases up to and including it (1 for v0.0.1), which the
  version string of the server shows, for example `26.3-1-main@abc1234`.
- **One release per commit.** A build of a commit that has a release tag already, for example when its run is started
  again, gets the version of that release and makes no new release. Runs of `main` run one at a time, and a running
  one is never cancelled, so two releases cannot get the same version; when more commits arrive while a run is going
  on, GitHub keeps only the newest waiting run, and the next release contains all of them.
- **A release contains** the Paperclip jar as `cubiq-<Minecraft version>-v<version>.jar`, its SHA-256 in a `.sha256`
  file, the source code of the bundled libraries whose license requires it to accompany the binary, and notes from
  `scripts/release-notes.py`: the commits since the previous release, the Purpur and Paper commits it is based on, and
  the license notices. Releases are marked as pre-releases while Cubiq is alpha software.
- **Source code of bundled libraries.** MySQL Connector/J is licensed under the GPLv2, which requires its source code
  to accompany the binary. `scripts/release-sources.py` fetches the source of each library marked with
  `attachSourceToReleases` in `scripts/library-notices.json`, at the commit recorded there, and archives it as
  `<artifact>-<version>-source.tar.gz`; the release and the snapshot attach these archives. When such a library changes
  its version, its entry gets the commit of the new version (see [Smoke tests](#smoke-tests)), and the archive follows.
- **The jar knows its release.** CI sets `CUBIQ_VERSION` and `BUILD_NUMBER` for the build, which end up in the
  manifest of the server jar as `Cubiq-Version` and `Build-Number`, and `/version` shows
  `You are running Cubiq v0.0.1`. Builds without `CUBIQ_VERSION` call themselves development builds.
- **The snapshot** is a pre-release with the tag `snapshot` that always holds the newest development build: every
  push to a branch of this repository other than `main` whose build passes all checks replaces it (job `snapshot`).
  Its jar is `cubiq-<Minecraft version>-snapshot.jar`, it has the same files as a release, and its notes list the
  commits since the latest release. The build records the branch as `snapshot` instead of the development branch's
  name; to rebuild a snapshot the way CI does, check it out on a branch named `snapshot`. Builds of pull requests
  publish nothing.
- **On other branches and in pull requests,** the summary of the build job shows which version the next release from
  `main` would get and a preview of its notes.
- The `release` and `snapshot` jobs request the permission to write the repository's contents for their
  `GITHUB_TOKEN`, which they need to create tags and releases. A ruleset that restricts creating `v*` tags or the
  `snapshot` tag would make them fail.

## Commits, branches and pull requests

- Use descriptive branch names such as `feature/region-scheduler`, `fix/chunk-loading`,
  `perf/entity-ticking` or `docs/architecture`.
- Write commit messages with a short imperative summary line and a body that explains why.
- Every commit must build: run `./gradlew applyAllPatches build` before pushing.
- Commit patches exactly as the `rebuild*` tasks write them. CI rebuilds all patches from the patched sources and
  fails if that changes a committed patch.
- Do not commit generated directories, build output, server run directories or secrets.

## Troubleshooting

- **HTTP 429 from Maven Central.** Machines behind a shared egress IP can be rate limited. Route
  Central through a mirror with a Gradle init script in `~/.gradle/init.d/` instead of changing the
  build, for example by rewriting `repo.maven.apache.org` to
  `https://maven-central.storage-download.googleapis.com/maven2/`.
- **A generated directory is in a broken state.** Re-run `./gradlew applyAllPatches`. As a last
  resort, run `./gradlew cleanCache` and apply again.
- **Rebuilding patches fails with `Unable to create '.../.git/index.lock': File exists`.** The rebuild tasks stage
  their patches with git and can collide when Gradle runs them in parallel. Run the rebuild again with
  `--max-workers=1`, as CI does.
